# Deployment guide (Helm: local kind/k3d and production-like k3s)

One chart (`charts/urumi`), two values files. Nothing else differs between environments.

| | `values-local.yaml` | `values-prod.yaml` |
|---|---|---|
| Domain | `localtest.me` | your domain (`global.domain`) |
| Scheme / cookies | http, cookie not `Secure`, `NODE_ENV=development` | https, `Secure` cookie, `__Host-` prefix, `NODE_ENV=production` (gateway refuses to start without `PUBLIC_ORIGINS` + secure cookies) |
| Ingress controller | ingress-nginx (+ 130 s timeout annotation for chat) | Traefik (k3s default), TLS via cert-manager |
| NetworkPolicy peer namespace | `ingress-nginx` | `kube-system` (Traefik) |
| Storage | cluster default class, 2 Gi | `local-path`, 20 Gi |
| Secrets | generated by the chart on first install, reused on upgrade (`lookup`) | pre-created by `scripts/create-prod-secrets.sh` (`secrets.existingSecret`), so values never enter Helm release history |
| Images | built locally, loaded into kind | pushed to your registry |
| LLM | `mock` (scripted, labelled) | `openai` (any OpenAI-compatible API) |

## Local domain approach
`shop.localtest.me` and `dashboard.localtest.me` resolve to `127.0.0.1` through public DNS (`localtest.me` is a wildcard record), so **no `/etc/hosts` edit is needed** and cookies/Origin checks behave like a real domain. kind maps host ports 80/443 to the ingress controller.
Offline? Add to `/etc/hosts`: `127.0.0.1 shop.localtest.me dashboard.localtest.me`.
Production DNS: two A records (`shop.<domain>`, `dashboard.<domain>`) to the VPS public IP; ports 80/443 open (80 is needed for the ACME HTTP-01 challenge).

## Local (kind + Calico + ingress-nginx)
Why Calico: kind's default CNI does **not enforce NetworkPolicy**; without an enforcing CNI the isolation in this chart would silently do nothing.
```bash
scripts/kind-up.sh            # kind cluster + Calico + ingress-nginx
scripts/build-images.sh       # builds 4 images, loads them into kind
scripts/install-local.sh      # helm upgrade --install (namespace labelled with Pod Security baseline)
scripts/smoke.sh              # endpoints, registered servers, NetworkPolicy isolation probes
```
Then follow the `NOTES.txt` output (it prints the exact `kubectl ... | base64 -d` commands for the admin API key and WordPress admin password).
k3d instead: `k3d cluster create urumi -p '80:80@loadbalancer'`, then `scripts/install-local.sh --set ingress.className=traefik --set networkPolicy.ingressControllerNamespace=kube-system --set ingress.gatewayAnnotations=null` (k3s enforces NetworkPolicy itself).

## Production-like VPS (k3s)
```bash
curl -sfL https://get.k3s.io | sh -                       # on the VPS (Traefik + local-path included)
# install cert-manager + a ClusterIssuer named letsencrypt-prod (see cert-manager docs)
REGISTRY=registry.example.com/urumi PUSH=1 scripts/build-images.sh
NS=urumi RELEASE=urumi scripts/create-prod-secrets.sh      # one-time; BACK UP GATEWAY_ENCRYPTION_KEY
kubectl label ns urumi pod-security.kubernetes.io/enforce=baseline --overwrite
helm upgrade --install urumi charts/urumi -n urumi -f charts/urumi/values-prod.yaml \
  --set global.domain=yourdomain.com --set gateway.llm.model=<model> --atomic --timeout 15m
```
The chart refuses to render with the placeholder domain.

### Required keys if you bring your own Secret (`secrets.existingSecret`)
`MARIADB_ROOT_PASSWORD, MARIADB_PASSWORD, WORDPRESS_ADMIN_PASSWORD, WC_CONSUMER_KEY (ck_...), WC_CONSUMER_SECRET (cs_...), WOO_MCP_TOKEN, UTILS_MCP_TOKEN, NOTES_MCP_TOKEN, GATEWAY_ENCRYPTION_KEY (base64 of 32 bytes), BOOTSTRAP_ADMIN_API_KEY (umk_<8>_<43>), SEED_SERVERS_JSON, OPENAI_API_KEY (may be empty)`.

## Upgrade and rollback
```bash
helm diff upgrade ...            # optional plugin: preview
helm upgrade urumi charts/urumi -n urumi -f charts/urumi/values-prod.yaml --atomic --timeout 15m   # --atomic rolls back automatically if pods never become Ready
helm history urumi -n urumi
helm rollback urumi <REVISION> -n urumi --wait
```
What rollback does and does not cover: it restores Kubernetes objects and image tags. It does **not** roll back data: MariaDB/WordPress volumes and the gateway SQLite file keep whatever the newer version wrote (the gateway only runs `CREATE TABLE IF NOT EXISTS`; there are no schema migrations yet). Take a volume/DB backup before upgrading a release that changes storage format. WordPress and the gateway use `Recreate` (RWO volume), so upgrades cause a short outage for those two.
Secrets are reused on upgrade (`lookup`) so DB passwords and the encryption key do not change.

## Public vs internal
Public (Ingress): storefront + wp-admin (`shop.<domain>`), dashboard (`dashboard.<domain>`), gateway at `dashboard.<domain>/api` and `/mcp`.
Internal only (ClusterIP, no Ingress, NetworkPolicy-restricted): woo-mcp (callable only by gateway), demo MCP servers (only gateway), MariaDB (only WordPress). WordPress is reachable by the ingress controller and woo-mcp only.
